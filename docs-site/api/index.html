API RESTREST API

Observer RMM expone una API REST en JSON para que otros sistemas —un ITSM, una CMDB, una mesa de ayuda o su propio tablero— lean el inventario de equipos y, si se les autoriza, operen sobre la flota. Todo lo que hace la consola web pasa por esta misma API: aquí se documentan sus 184 rutas y 264 operaciones, y cómo autenticarse con una API key.

Observer RMM exposes a JSON REST API so other systems —an ITSM, a CMDB, a help desk or your own dashboard— can read the device inventory and, if authorized, act on the fleet. Everything the web console does goes through this same API: this page documents its 184 routes and 264 operations, and how to authenticate with an API key.

Inicio rápidoQuick start

La API vive en el nombre de host API de su servidor Observer RMM —el mismo que usa la consola, normalmente https://api.su-dominio.cl— y se consume sólo por HTTPS. Cada solicitud lleva la clave en el encabezado X-API-KEY:

The API lives on the API hostname of your Observer RMM server —the same one the console uses, typically https://api.your-domain.com— and is served over HTTPS only. Every request carries the key in the X-API-KEY header:

curl -s https://api.su-dominio.cl/agents/?detail=false \
  -H "X-API-KEY: ABCDEFGHIJKLMNOPQRSTUVWXYZ012345" \
  -H "Accept: application/json"

La respuesta es un arreglo JSON con los equipos que el usuario dueño de la clave puede ver. El nombre de host de la API es el mismo al que se conecta el navegador al iniciar sesión en la consola.

The response is a JSON array with the devices the key's owner can see. The API hostname is the same one the browser connects to when you sign in to the console.

Cómo obtener una API keyHow to get an API key

Una API key actúa en nombre de un usuario de Observer RMM y hereda exactamente sus permisos. Por eso la práctica recomendada es crear un usuario de servicio dedicado a la integración, con un rol de sólo lectura, y generarle la clave. Lo hace un administrador desde la consola web del servidor RMM:

An API key acts on behalf of an Observer RMM user and inherits exactly that user's permissions. The recommended practice is therefore to create a dedicated service user for the integration, with a read-only role, and issue the key to it. An administrator does this from the RMM server's web console:

  1. Cree un rol para la integración. Configuración → Gestor de permisos → nuevo rol (p. ej. «Integración ITSM»). Marque sólo lo que la integración necesita leer, por ejemplo Listar agentes, Listar clientes, Listar sitios y Listar software. En Clientes permitidos / Sitios permitidos puede acotar la visibilidad (vacío = todos).
  2. Cree el usuario de servicio. Configuración → Administración de usuarios → nuevo usuario con ese rol. Active Denegar inicios de sesión al panel: el usuario existirá sólo para la API y nadie podrá entrar a la consola con él.
  3. Genere la clave. Configuración → Configuración global → Claves de API → Agregar clave. Indique un Nombre descriptivo, elija el Usuario de servicio y, opcionalmente, una Expiración de la clave. El servidor genera una clave aleatoria de 32 caracteres, visible en la tabla de claves.
  4. Entregue la clave por un canal seguro (gestor de contraseñas, no correo en claro) al equipo que opera la integración.
  1. Create a role for the integration. Settings → Permissions Manager → new role (e.g. “ITSM integration”). Tick only what the integration needs to read, for example List Agents, List Clients, List Sites and List Software. Use Allowed Clients / Allowed Sites to narrow visibility (empty = all).
  2. Create the service user. Settings → User Administration → new user with that role. Enable Deny Dashboard Logins: the user exists only for the API and nobody can sign in to the console with it.
  3. Generate the key. Settings → Global Settings → API Keys → Add key. Enter a descriptive Name, pick the service User and, optionally, a Key Expiration. The server generates a random 32-character key, shown in the keys table.
  4. Hand the key over through a secure channel (a password manager, not plain email) to the team running the integration.

Permisos Para ver y crear claves, el administrador necesita en su propio rol Listar claves de API y Gestionar claves de API. Una clave se revoca eliminándola de la misma tabla, con efecto inmediato.

Permissions To view and create keys, the administrator's own role needs List API Keys and Manage API Keys. A key is revoked by deleting it from the same table, effective immediately.

Autenticación y permisosAuthentication and permissions

  • Encabezado: X-API-KEY: <clave> en cada solicitud. No hay sesión, cookies ni renovación de tokens.
  • Permisos: cada operación exige un permiso del rol del usuario dueño de la clave; la columna Permiso del rol de la referencia lo indica con el mismo nombre que muestra la consola.
  • Visibilidad: los listados se recortan a los Clientes permitidos y Sitios permitidos del rol; un equipo fuera de ese alcance responde como si no existiera.
  • Respuestas de error: 401 clave inválida, expirada o de un usuario inactivo · 403 el rol no tiene el permiso · 404 el recurso no existe o no es visible · 400 datos inválidos (el cuerpo trae el motivo en texto).
  • Auditoría: las acciones hechas con la clave quedan en la auditoría a nombre del usuario de servicio.
  • Header: X-API-KEY: <key> on every request. There are no sessions, cookies or token refreshes.
  • Permissions: every operation requires a permission on the key owner's role; the Role permission column of the reference names it exactly as the console shows it.
  • Visibility: listings are trimmed to the role's Allowed Clients and Allowed Sites; a device outside that scope behaves as if it did not exist.
  • Error responses: 401 invalid or expired key, or inactive user · 403 the role lacks the permission · 404 the resource does not exist or is not visible · 400 invalid data (the body explains why, as text).
  • Audit: actions performed with the key are recorded in the audit log under the service user.

ConvencionesConventions

  • JSON de entrada y salida (Content-Type: application/json). Fechas en ISO 8601 y UTC.
  • La barra final es obligatoria: /agents/, no /agents.
  • Equipos: las rutas usan el agent_id (cadena larga única por equipo), no el id numérico. Obténgalo del listado GET /agents/.
  • Consultas con filtros: algunos listados grandes (alertas, auditoría, historial de chequeos) se consultan con PATCH y los filtros en el cuerpo JSON; son lecturas, no modifican nada.
  • Acciones sobre equipos (comandos, scripts, reinicios) se entregan al agente en línea; si el equipo está apagado la operación falla o queda como acción pendiente.
  • JSON in and out (Content-Type: application/json). Dates in ISO 8601 and UTC.
  • The trailing slash is required: /agents/, not /agents.
  • Devices: routes use the agent_id (a long string unique per device), not the numeric id. Get it from the GET /agents/ listing.
  • Filtered queries: some large listings (alerts, audit log, check history) are queried with PATCH and the filters in the JSON body; they are reads and change nothing.
  • Device actions (commands, scripts, reboots) are delivered to the online agent; if the device is off the operation fails or is queued as a pending action.

Ejemplos: curl, PowerShell y PythonExamples: curl, PowerShell and Python

curl

# Equipos de un cliente / Devices of one client
curl -s "https://api.su-dominio.cl/agents/?client=3" -H "X-API-KEY: $OBSERVER_API_KEY"

# Ficha de un equipo / One device's record
curl -s "https://api.su-dominio.cl/agents/{agent_id}/" -H "X-API-KEY: $OBSERVER_API_KEY"

PowerShell

$h = @{ "X-API-KEY" = $env:OBSERVER_API_KEY }
$agents = Invoke-RestMethod -Uri "https://api.su-dominio.cl/agents/" -Headers $h
$agents | Select-Object hostname, serial_number, operating_system, client_name, site_name, status |
  Export-Csv inventario.csv -NoTypeInformation -Encoding UTF8

Python

import os, requests

API = "https://api.su-dominio.cl"
s = requests.Session()
s.headers.update({"X-API-KEY": os.environ["OBSERVER_API_KEY"]})

for a in s.get(f"{API}/agents/", timeout=60).json():
    sw = s.get(f"{API}/software/{a['agent_id']}/", timeout=60).json()
    print(a["hostname"], a["serial_number"], a["status"], len(sw.get("software", []) if sw else []))

Buenas prácticas de seguridadSecurity best practices

  • Mínimo privilegio: una integración de inventario no necesita permisos de comandos, scripts, reinicios, registro ni borrado. Si nunca los tiene, una clave filtrada no puede operar la flota.
  • Nunca asocie la clave a un superusuario: un superusuario tiene todos los permisos y la clave también.
  • Una clave por integración, con nombre que la identifique, para poder revocarla sin afectar a las demás.
  • Expiración y rotación: fije una expiración y rote la clave periódicamente; guárdela en un gestor de secretos, nunca en el código.
  • Restrinja el origen: si el ITSM tiene IP fija, pídale a su administrador que limite el acceso a la API a esa IP en el proxy o firewall.
  • Operaciones destructivas (borrado remoto, desinstalación de agentes, modo perdido) exigen permisos propios, que ningún rol de integración debería tener.
  • Least privilege: an inventory integration needs no command, script, reboot, registry or wipe permissions. If it never has them, a leaked key cannot operate the fleet.
  • Never tie the key to a superuser: a superuser has every permission, and so does its key.
  • One key per integration, with a name that identifies it, so it can be revoked without affecting the others.
  • Expiration and rotation: set an expiration and rotate the key periodically; keep it in a secrets manager, never in code.
  • Restrict the source: if the ITSM has a fixed IP, ask your administrator to limit API access to that IP at the proxy or firewall.
  • Destructive operations (remote wipe, agent uninstall, lost mode) require their own permissions, which no integration role should have.
